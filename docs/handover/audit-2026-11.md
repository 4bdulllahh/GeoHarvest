# Audit and research, 2026-11-16 (M2 of the v0.3.3 plan)

Three read-only audits and one web research run, done by cheaper models. Nothing was run or
reproduced: **read the code at each reference before fixing it**. Line numbers are from
commit `62669f6`. Spot-checked by the main model: the two lambdas (A1), Run again calling
`start()` (A2), the unreadable key store starting clean (F1). The milestone letters match
the table in [../../handover.md](../../handover.md). Delete a row when it is fixed.

## Research: how other Google Maps scrapers plan searches

Read: gosom/google-maps-scraper, omkarcloud/google-maps-scraper, Mahanaicoach/google-maps-scraper-kit
(READMEs only, their source was not read), two Apify listings (marketing claims).

- **Nothing beats the plain HTTPS method** the app already uses. The others drive a browser.
- **Worth copying: split only when capped.** Run an area; if it returns a full list, split it
  into 4 smaller areas and go again, deduping by place id. GeoHarvest splits every capped city
  search into a fixed grid all at once (694 views in the user's search).
- **Cell sizes:** gosom defaults to 1 km cells (0.5 km in examples). GeoHarvest's are up to 5 km.
- **Nobody handles near-synonym types** (builder, contractor): that plan has to be our own.
- **No tool publishes numbers** for delays, backoff or Google's limit. The kit retries a
  limited keyword twice, then stops and keeps what it has. Our numbers must come from testing.
- Not verified: any split threshold or depth, whether the cap is 120 or 200.

## Findings, grouped by the milestone that fixes them

### M4: leads keep their marks
- `search.py:639` `set_picked`: DELETE and re-insert are two commits. Loses `exported` and
  `created`; a crash or a UI read in between sees 0 leads. One transaction, carry both over.
- `search.py:615` `check_candidate` overwrites `dropped`, so a lead deleted while its website
  or AI check is in flight comes back. Same window in `keep()` (reads fits, then re-inserts).
- `search.py:707` `delete_leads`: the `(? = 0 OR search_id = ?)` form can't use the primary key
  and there is no index on `candidates(place_id)`: 1,000 deletes = 1,000 table scans.

### M5: shorter batches, leads live
- Nothing tells the Leads page about new leads during a search (`lead_updated` is only emitted
  by AI scoring, `leads.py:518`). It shows the snapshot from the start until the run ends.
- `scrape.py:103` the "queries keep failing" test counts fitting candidates after the website
  check. A batch whose 100 new ones are all dropped looks like no progress: ends as "stopped".
  Count rows or pages fetched.

### M6: faster saving
- `search.py:598` `candidates()` parses every fitting row; `scrape.py:88,103,124` call it for
  `len()`. Use COUNT. Add `CREATE INDEX candidates_dropped ON candidates(search_id, dropped)`.
- `search.py:248` `why_not` rebuilds the country set for every lead, under the page lock.
- `search.py:379` `deep_queries`: one `json_extract` scan of all candidates per done query
  (500 queries x 30,000 rows). Group by query in one pass.
- `scraper.py:253` one extra request per query to find the empty last page. A page with fewer
  than `PAGE_SIZE` raw results could end it.

### M7: similar types, smarter digging
- `search.py:379-384` `deep_queries` counts only candidates whose stored `query` is this one,
  but `INSERT OR IGNORE` keeps the first query that found a business. Overlapping types fall
  under `DEEP_AT` and are never deepened (plausible).
- `search.py:390` `partition(" in ")` breaks on a type containing " in "; use `rpartition`.
- `scrape.py:137` duplicate queries (a repeated type or city) share one generator between two
  threads: "generator already executing". Dedupe in `build_queries`.

### M8, M9: Google's limit
- `scraper.py:136-156` a proxy that was limited is not sidelined: every Nth request still
  starts on it.
- `scrape.py:108-116` Stop while blocked skips `wait_for_google`, so closing the app while
  limited resumes straight into Google.

### M11: opening hours
- `search.py:346-357` the hours options are ANDed. Open now + Open at 20:00 Friday is almost
  never true. `open_now` is judged when each candidate is saved and stored for good in
  `dropped`, so a resumed search judges by a different time.

### M12: update later
- `main_window.py:641` `_install_update` only checks for a worker. A "waiting" search has none,
  so its countdown can start a search while the update notice is open.

### M13: tidy up storage. A safe clean-up must keep:
1. Every row with `dropped` = `REMOVED` ("deleted by you") or `KNOWN`.
2. The `place_id` of every candidate (`INSERT OR IGNORE` is what stops re-adding).
3. All rows of a search that can still run or be widened (running, stopped, paused, waiting,
   interrupted): `undrop`, `dropped_counts`, the "listed" total and `is_age_reason` read them.
4. `latitude`, `longitude`, `query` for searches that may still be deepened.
5. Safe to trim: `data` of dropped rows in `done` searches. Fitting rows stay whole.

### A: search screens (New search, Past searches)
- A1 `history.py:75`, `leads.py:261`: `search_finished` connected to a lambda. After F5 the
  old page is deleted but the lambda still fires: "wrapped C/C++ object has been deleted".
  Use `Page.guard` or a bound method.
- A2 `search.py:646` `start()` never checks `self.worker`; `history.py:130` Run again calls it.
  With a search running it creates a "running" row that never runs, which auto-resumes at the
  next launch. Resume has the same stale state. History buttons only refresh on show or
  selection (`history.py:89`), never when a worker starts or ends.
- A3 `search.py:765` `pick_up` with no record hides the tiles but not `summary` or `widen`.
  Clicking a widen button then reaches `searches.get(None)["options"]`: TypeError.
- A4 `leads.py:269`: after a search is deleted, Leads keeps its rows under "All searches";
  exports and deletes run against the stale id.
- A5 `search.py:754,785` `load_options` overwrites the form on every auto-resume and on
  `_show_unfinished`: a user filling in a new search loses what they typed.
- A6 `search.py:724` `stop()` overwrites `ending`: Stop or Pause, then close the app, and the
  search auto-resumes next launch.
- A7 `search.py:959` `_on_failed` does not refresh Leads, History or the status bar, and shows
  Start next to Resume.
- A8 `scrape.py:108` Pause or Stop pressed as the search completes: status paused or stopped
  instead of done.
- A9 `main_window.py:678` the "search still running" close prompt also fires for AI scoring.
- A10 `search.py:704` the AI tile shows when Smart is in the saved options but no AI is set up.

### B: the search job never gets stuck
- B1 `scraper.py:48,50` `decode()` can raise KeyError or IndexError; `scrape.py:173` catches
  only `httpx.HTTPError` and `ValueError`. The error escapes, the status stays "running", and
  every launch auto-resumes into the same error. Catch in `run()` and `work()`, set the status.
- B2 `scrape.py:253` nobody reads the website-check futures: an error in `check_candidate`
  vanishes and the lead is never checked again in this run.
- B3 `main_window.py:659` `workers.shutdown(2000)` ignores its result; `scrape.py:181` has an
  uninterruptible `time.sleep(3)`; an update download is never cancelled on close.
- B4 `base.py:59,113` worker errors go to `traceback.print_exc()` only: nowhere in the
  installed app. Log them to crash.log. The weekly auto backup fails silently the same way.
- B5 `run.py:33` crash.log has no size limit; the start-up failure path rewrites it with "w".

### C: Leads page speed (30,000 rows)
- C1 `leads.py:444` `_mark_exported` calls `model.update` per lead (30,000 `dataChanged`),
  plus `to_tsv` on the UI thread.
- C2 `leads.py:176` "All searches": `all_leads()`, a haystack per row and `empty_columns()`,
  all on the UI thread; `select_search` can load twice.
- C3 `search.py:787` `_show_unfinished` parses every candidate on the UI thread, 800 ms after
  launch and after every pause.
- C4 `search.py:352` every `setChecked` in `load_options` re-runs `build_queries`.

### D: backups
- D1 `backup.py:52` `restore_backup` never runs the schema after restoring. An older backup
  has no `candidates` table until restart. `db.py:66` stamps `user_version` without reading it:
  there are no migrations.
- D2 `settings.py:213` backup and restore run on the UI thread (a 140 MB copy; retries forever
  on a lock).
- D3 `backup.py:27` backups are written straight to the final name; a partial auto backup
  counts towards `AUTO_KEEP` and pushes out good ones.
- D4 `backup.py:55` the safety backup name is to the minute: two restores in a minute overwrite
  the original data. These files are never pruned.

### E: exports
- E1 `exporter.py:163` `to_tsv`: `"" in "=+-@"` is True, so every empty cell is pasted as `'`
  (not spot-checked).
- E2 `exporter.py:48,56,148` files written straight to the final path.
- E3 `exporter.py:29,74` lists of lists and dicts are written as Python repr; NaN can corrupt xlsx.
- E4 `exporter.py:37` `_PHONE` lets `+1-1` through as a formula; leading tab or CR not covered.
- E5 `exporter.py:134` `to_crm` breaks if `emails` is a list; HomingPigeon export drops
  leads with no email without saying so.

### F: saved keys
- F1 `credentials.py:120` an unreadable store is treated as empty, and the next save overwrites
  it: every other key and the proxy list are gone. Keep the old file as `.bak` and log it.
- F2 `credentials.py:97` if DPAPI fails, falls through to Fernet under a guessable machine key
  (and `cryptography` may not be bundled). On Windows, fail with a plain message instead.

### G: Smart mode
- G1 `ai.py:287` `response.json()` not wrapped: a 200 with HTML shows a raw exception. 400-class
  errors (no balance, bad model) are non-fatal, so every batch fails in turn.
- G2 `scrape.py:280` a lead the AI returned no score for is sent again every batch and counted
  again against the user's limit.
- G3 `workers/ai.py:28` KeyError if the search was deleted.
- G4 `search.py:559` `update_lead` and `check_candidate` are read-modify-write without a
  transaction: AI scoring and the search can overwrite each other's fields.

### H: website checks
- H1 `enrich.py:338` the site is read only `if find_contacts or site_text`, but it is visited
  for `find_owner` and the require options too: with `require_email` on and `find_emails` off,
  every lead is dropped as "no email found" (check whether the UI allows it).
- H2 `enrich.py:306` a 429 or 5xx from RDAP is cached as "no record": the age filter lets
  everything through.
- H3 `enrich.py:114` "Info@Acme.Com" is stored as "info@acme.c".

### I: Setup
- I1 `installer/setup_app.py:530` uninstall deletes the whole install folder with no check that
  it is a GeoHarvest folder (a custom `/DIR=` pointing at Documents would be wiped).
- I2 `db.py:102` no rollback on error: a failed write can hold the lock on that thread.
